# SaaS licence issuance and POS compatibility

## Existing contract is the compatibility boundary
The current POS documentation specifies Ed25519 licence key format:
`base64url(payload JSON).base64url(signature)`.
Payload v1: `{ v:1, licensee, hardwareId, issuedAt, expiresAt, seats:{terminals,captains,kds}, features }`.
The POS embeds only the public key and verifies locally. Hardware ID is generated by the existing Windows implementation. Do not create a new payload or hardware-ID algorithm in SaaS without a deliberate versioned migration.

## Issuer design
- Private Ed25519 key held in cloud secret manager/KMS-backed signing service; never in Git, browser, POS installer or PostgreSQL.
- Public key remains embedded in POS verifier.
- Issuer accepts only trusted internal calls after checking subscription/trial entitlement and hardware binding.
- Persist licence ID, outlet, hardware fingerprint reference, payload version, issued/expiry timestamps, key ID, status and signed-key hash. Signed key can be stored by hub according to current renewal flow; avoid unnecessary duplicate plaintext storage.
- Key rotation requires a key ID/version strategy and staged public-key rollout. Existing v1 verifier has no key ID; do not rotate until verifier supports multiple public keys or a coordinated release.

## Trial and paid licence
- Trial expires 14 days after successful provisioning.
- Paid licence expiry follows paid-through subscription period.
- Never issue a licence that shortens a currently installed valid paid licence accidentally.
- Map plan entitlements to existing seats/features. Reject activation if seats exceed entitlement.
- Hardware replacement requires verified owner action and audit trail.

## Hub integration
Existing outlet sync agent fetches `GET /v1/pos/licence` hourly from the DinePOS cloud hub and installs a valid later-ending key. Implement a trusted SaaS-to-hub adapter that updates the existing store licence using a server-side credential. Do not expose `HUB_ADMIN_KEY` to a browser or customer API response. Inspect actual hub source and tests before finalizing the exact route.

## Offline and expiry semantics
The outlet validates signature locally. Cloud revocation cannot instantly reach a disconnected PC. Preserve existing local clock rollback checks, seven-day grace and rule: never interrupt an open business day; no new business day after licence enforcement says invalid/expired. Customer portal must show last hub contact and licence expiry separately from subscription status.

## Acceptance
- Golden test vectors generated by current keygen verify in POS.
- Wrong hardware, tampered payload and invalid signature fail.
- Existing key remains accepted after SaaS integration.
- Renewals never shorten installed licence.
- Offline POS continues local operation according to existing policy.
- Private key is absent from repository, build artifacts, logs and database.
